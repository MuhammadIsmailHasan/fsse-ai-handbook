## 🧠 The big idea

An EC2 instance should be treated like a **rental car, not a family pet**. You don't name it, nurse it and repair it by hand for years — you write down what it must be (AMI + instance type + user data + role + security group) so a fresh one can replace it any time.

Two habits follow from that:

- Data that matters lives **outside** the server (RDS, S3), because the car can be returned at any moment.
- You get in through a **controlled front desk** (Session Manager), not a key hidden under the doormat (SSH open to the world).

## ❓ Why it matters

EC2 is the most flexible compute on AWS: it's how you'll first run RevoShop's Compose stack in the cloud, and many other services are built on it. Most EC2 security incidents come from open SSH, stolen keys, unpatched software, or instance credentials stolen through a web bug — all preventable with the settings in this lesson.

Done carelessly:

- SSH open to `0.0.0.0/0` with a `.pem` key emailed around; bots try passwords all day.
- The server was set up by hand over SSH, so six months later nobody can rebuild it.
- A `t3.micro` runs out of CPU credits and the API becomes ten times slower "for no reason".
- The instance is terminated and its root disk — with uploads and the database — disappears with it.
- A bug in the app lets an attacker read `http://169.254.169.254/` and steal the server's AWS credentials (that's IMDSv1).

## 📖 Step by step

### 1. Instance types

```text
t4g.small
│ │  └── size: nano, micro, small, medium, large, xlarge…
│ └──── g = Graviton (arm64)   (no letter or i/a = x86_64 Intel/AMD)
└────── family: t = burstable general purpose · m = general · c = compute · r = memory
```

| Family | For |
|---|---|
| `t3`/`t4g` (burstable) | small web apps with spiky, low average CPU |
| `m7i`/`m7g` | steady general workloads |
| `c7g` | CPU-heavy (image processing, encoding) |
| `r7g` | memory-heavy (caches, large JVM/Python processes) |

**Burstable CPU credits**: `t` instances earn credits when below their baseline and spend them when above. `t3`/`t4g` default to **unlimited** mode (you pay for surplus credits if average usage stays above baseline) — watch `CPUCreditBalance` and `CPUSurplusCreditsCharged`.

**Architecture must match your image**: a `linux/amd64` image needs an x86 instance (`t3`), a `linux/arm64` image needs Graviton (`t4g`). Multi-arch images (Week 1) remove the constraint.

### 2. AMIs

| AMI | Notes |
|---|---|
| **Amazon Linux 2023** | AWS-optimized, SSM agent preinstalled, `dnf`, predictable updates |
| **Ubuntu 24.04 LTS** | familiar, huge ecosystem, `apt install docker.io docker-compose-v2`, SSM agent preinstalled on official AMIs |
| Your own AMI (Packer / EC2 Image Builder) | faster boots, golden images for fleets |

Use the **latest** official AMI (look it up via SSM public parameters, e.g. `/aws/service/canonical/ubuntu/server/24.04/stable/current/amd64/hvm/ebs-gp3/ami-id`), not an ID copied from a blog.

### 3. User data and cloud-init

User data is the **note you leave for the cleaner**: the server reads it once, on its very first boot, and follows it. Write it down and any new server sets itself up the same way.

```yaml
#cloud-config
package_update: true
package_upgrade: true
packages: [docker.io, docker-compose-v2, unattended-upgrades]
users:
  - default
  - name: deploy
    groups: docker
    shell: /bin/bash
    lock_passwd: true
write_files:
  - path: /etc/docker/daemon.json
    content: '{"log-driver": "json-file", "log-opts": {"max-size": "10m", "max-file": "3"}}'
runcmd:
  - [systemctl, enable, --now, docker]
```

- Runs **once** on first boot (as root). Logs: `/var/log/cloud-init-output.log`.
- **Never put secrets in user data** — it's readable through the EC2 API and the metadata service. Fetch secrets at runtime from SSM (Week 4).
- Limit: 16 KB.

### 4. Instance roles instead of keys

An instance profile is a **staff badge clipped to the car**, not a key you copy: AWS hands the server temporary credentials automatically, and they refresh by themselves.

An **instance profile** attaches an IAM role; the AWS SDKs and CLI on the instance pick up temporary credentials automatically.

| Managed policy / permission | Why |
|---|---|
| `AmazonSSMManagedInstanceCore` | Session Manager, Run Command, patching |
| `ssm:GetParametersByPath` on `/revoshop/production/*` (+ `kms:Decrypt` for the key) | read app secrets at deploy time |
| `CloudWatchAgentServerPolicy` | ship logs/metrics with the CloudWatch agent (optional) |

### 5. Session Manager, not SSH

```bash
aws ssm start-session --target i-0123456789abcdef0                      # a shell, no port 22, no key pair
aws ssm start-session --target i-0123… \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["revoshop.xxxx.rds.amazonaws.com"],"portNumber":["5432"],"localPortNumber":["5494"]}'
# then: psql "postgresql://…@localhost:5494/revoshop"                   # reach private RDS from your laptop
```

Needs the Session Manager plugin for the AWS CLI on your laptop, the instance role above, and outbound HTTPS from the instance. Sessions are logged in CloudTrail; you can record session output to S3/CloudWatch.

### 6. IMDSv2

IMDSv1 answers anyone who asks; IMDSv2 first requires a token, like a receptionist who asks for your name before handing over the badge. That one setting blocks a whole family of attacks.

The instance metadata service (`169.254.169.254`) hands out role credentials. **IMDSv2** requires a session token obtained with a `PUT` request, which blocks most SSRF attacks. Set **metadata version: V2 only** (and hop limit 1, or 2 if containers must reach it) on every instance.

### 7. EBS storage

| Behavior | Detail |
|---|---|
| **gp3** | default choice; set size, IOPS and throughput independently |
| Encryption | enable **EBS encryption by default** for the account/region |
| Stop | instance stops; EBS volumes (and their cost) remain; public IP changes (unless Elastic IP) |
| Terminate | root volume deleted if "delete on termination" (default for root); extra volumes may remain and keep billing |
| **Snapshots** | incremental backups to S3-backed storage; automate with **Data Lifecycle Manager** or AWS Backup |

### 8. Public IPs, Elastic IPs, protection

- Auto-assigned public IPv4 changes on stop/start; an **Elastic IP** stays with you (both billed hourly per IPv4).
- **Termination protection** and **stop protection** prevent console accidents.
- Name and tag instances; enable **detailed monitoring** only if you need 1-minute metrics.

### 9. Monitoring and patching

- CloudWatch basic metrics: CPU, network, status checks. Memory and disk need the **CloudWatch agent**.
- Alarms: `StatusCheckFailed` (with an automatic **recover** action), CPU credit balance, disk usage (agent).
- Patching: `unattended-upgrades` for security updates, plus a monthly rebuild from a fresh AMI; **SSM Patch Manager** for fleets.

### Choosing your setup

Every option here is a trade-off:

| Choice | ✅ | ❌ |
|---|---|---|
| EC2 + Docker Compose | full control, cheapest always-on option for small apps, same stack as local | you patch, monitor and scale the OS; single instance = single point of failure |
| Graviton (`t4g`) | lower price for similar performance | needs arm64 images |
| Session Manager | no open ports, no keys, audited | needs agent + role + outbound HTTPS; small setup |
| SSH with keys | universal | key sprawl, open port, harder auditing |
| Elastic IP | stable DNS target | IPv4 charge; better to put a load balancer in front for real production |

- ✅ Small always-on apps, custom software, learning how servers work, workloads needing special OS access.
- ✅ Behind a load balancer in an Auto Scaling group for stateless fleets.
- 🚫 Don't run a single EC2 instance as the only copy of important data.
- 🚫 Don't hand-configure production servers you can't recreate from code.

## ⚠️ Common mistakes

- Deploying an `arm64` image built on a Mac to an x86 instance (`exec format error`).
- Security group allowing SSH from anywhere "just for today".
- Assuming the public IP stays the same after stopping the instance.
- Writing secrets into user data or AMIs.

## 🏆 Best practices

- [ ] Latest official AMI; architecture matches your images.
- [ ] Right-size with measurements; watch CPU credits on burstable instances.
- [ ] Bootstrap with user data/cloud-init (no secrets); rebuildable from scratch.
- [ ] IAM instance role with least privilege; no access keys on the instance.
- [ ] Session Manager; no inbound SSH; no key pair unless you truly need one.
- [ ] IMDSv2 required.
- [ ] Encrypted gp3 volumes; automated snapshots for anything stateful; delete orphaned volumes.
- [ ] Status-check alarm with auto-recover; security updates enabled; termination protection.
- [ ] Tags: project, environment, owner.

:::quiz
Show a possible specification

- **AMI:** Ubuntu 24.04 LTS, looked up via `aws ssm get-parameters --names /aws/service/canonical/ubuntu/server/24.04/stable/current/amd64/hvm/ebs-gp3/ami-id`.
- **Type:** `t3.small` (x86 matches CI images), credit specification `standard` to cap spend (or `unlimited` with a surplus-credits alarm).
- **Network:** `public-a` subnet, **Elastic IP** (stable DNS for Caddy/Let's Encrypt and Midtrans), security group `sg-web`: 80 and 443 from `0.0.0.0/0` and `::/0`; **no port 22**.
- **Role:** `revoshop-ec2` with `AmazonSSMManagedInstanceCore` + inline policy `ssm:GetParametersByPath`/`GetParameter` on `arn:aws:ssm:<region>:<account>:parameter/revoshop/production/*` + `kms:Decrypt` on the AWS-managed SSM key.
- **Metadata:** IMDSv2 required, hop limit 2 (Docker containers).
- **Storage:** 20 GiB gp3, encrypted, delete on termination (no state on the instance).
- **User data:** exercise 04 output (Docker, compose plugin, deploy user, log rotation, swap 1 GB, app dir) — no secrets.
- **Tags:** `Name=revoshop-prod-1`, `Project=revoshop`, `Env=production`, `Owner=ismail`.
- **Protection:** termination protection on.
- **Alarms:** `StatusCheckFailed_System` → recover action; `CPUCreditBalance < 20`; RDS alarms separately.
- **Replacement:** launch a new instance from the same spec → deploy the same image digest (reads secrets from SSM) → smoke test against its IP → move the Elastic IP → terminate the old instance. Data is safe because PostgreSQL is on RDS, images on S3, and Redis holds only cache/rate-limit data.

## ✅ Quick check

:::quiz
Your API on a `t3.small` is fast in the morning and slow every afternoon, with CPU "only" at 30%. What do you check?

The CPU credit balance and baseline: a `t3.small`'s baseline is 20% per vCPU. If credits are exhausted (standard mode) the instance is throttled to baseline; in unlimited mode you'd see surplus credit charges instead. Consider a larger or non-burstable instance, or reduce CPU use.
:::

:::quiz
Why does IMDSv2 help against SSRF?

Getting credentials requires first obtaining a token with an HTTP `PUT` and a custom header, which typical SSRF vulnerabilities (that only make `GET` requests to a URL) can't do; the hop limit also stops forwarded requests.
:::
