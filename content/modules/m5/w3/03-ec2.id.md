## 🧠 Ide besarnya

Satu EC2 instance harus diperlakukan seperti **rental mobil, bukan hewan peliharaan keluarga**. Kamu tidak kasih nama, rawat, dan perbaiki dengan tangan selama bertahun-tahun — kamu tulis apa yang harus dimiliki (AMI + tipe instance + user data + role + security group), jadi satu yang baru bisa menggantinya kapan saja.

Dua kebiasaan mengikuti dari itu:

- Data yang penting hidup **di luar** server (RDS, S3), karena mobilnya bisa dikembalikan kapan saja.
- Kamu masuk lewat **resepsionis terkontrol** (Session Manager), bukan kunci yang disembunyikan di bawah pintu (SSH terbuka ke dunia).

## ❓ Kenapa ini penting

EC2 adalah compute paling fleksibel di AWS: itu cara pertama kamu menjalankan stack Compose RevoShop di cloud, dan banyak service lain dibangun di atasnya. Sebagian besar insiden keamanan EC2 datang dari SSH terbuka, key yang dicuri, software yang tidak terpatch, atau credential instance yang dicuri lewat bug web — semuanya bisa dicegah dengan pengaturan di materi ini.

Kalau dikerjakan sembarangan:

- SSH terbuka ke `0.0.0.0/0` dengan key `.pem` dikirim email; bot coba password sepanjang hari.
- Server diatur dengan tangan lewat SSH, jadi enam bulan kemudian tidak ada yang bisa membangunnya lagi.
- `t3.micro` kehabisan CPU credit dan API jadi sepuluh kali lebih lambat "tanpa alasan jelas".
- Instance dihapus dan root disk-nya — dengan upload dan database — hilang bersamanya.
- Bug di app biarkan attacker baca `http://169.254.169.254/` dan curi credential AWS server itu (itulah IMDSv1).

## 📖 Langkah demi langkah

### 1. Tipe instance

```text
t4g.small
│ │  └── size: nano, micro, small, medium, large, xlarge…
│ └──── g = Graviton (arm64)   (no letter or i/a = x86_64 Intel/AMD)
└────── family: t = burstable general purpose · m = general · c = compute · r = memory
```

| Keluarga | Untuk |
|---|---|
| `t3`/`t4g` (burstable) | aplikasi web kecil dengan CPU yang lompat-lompat, rata-rata rendah |
| `m7i`/`m7g` | beban kerja general yang stabil |
| `c7g` | CPU-heavy (pengolahan gambar, encoding) |
| `r7g` | memory-heavy (cache, proses JVM/Python besar) |

**CPU credit burstable**: instance `t` kumpulkan credit saat di bawah baseline, dan pakai saat di atas. `t3`/`t4g` default ke mode **unlimited** (kamu bayar surplus credit jika rata-rata usage tetap di atas baseline) — awasi `CPUCreditBalance` dan `CPUSurplusCreditsCharged`.

**Arsitektur harus cocok dengan image-mu**: citra `linux/amd64` butuh instance x86 (`t3`), citra `linux/arm64` butuh Graviton (`t4g`). Citra multi-arch (Minggu 1) hapus batasan itu.

### 2. AMI

| AMI | Catatan |
|---|---|
| **Amazon Linux 2023** | AWS-optimized, SSM agent sudah terpasang, `dnf`, update bisa diprediksi |
| **Ubuntu 24.04 LTS** | familiar, ekosistem besar, `apt install docker.io docker-compose-v2`, SSM agent sudah terpasang di AMI resmi |
| AMI kamu sendiri (Packer / EC2 Image Builder) | boot lebih cepat, golden image untuk fleet |

Pakai **latest** AMI resmi (cari lewat SSM public parameter, misalnya `/aws/service/canonical/ubuntu/server/24.04/stable/current/amd64/hvm/ebs-gp3/ami-id`), bukan ID yang disalin dari blog.

### 3. User data dan cloud-init

User data adalah **catatan yang kamu tinggal untuk pembersih**: server membacanya sekali, pada boot paling pertama, dan mengikutinya. Tulis saja, dan server baru mengatur dirinya sendiri dengan cara yang sama.

```yaml
#cloud-config
package_update: true
package_upgrade: true
packages: [docker.io, docker-compose-v2, unattended-upgrades]
users:
  - default
  - name: deploy
    groups: docker
    shell: /bin/bash
    lock_passwd: true
write_files:
  - path: /etc/docker/daemon.json
    content: '{"log-driver": "json-file", "log-opts": {"max-size": "10m", "max-file": "3"}}'
runcmd:
  - [systemctl, enable, --now, docker]
```

- Berjalan **sekali** pada first boot (sebagai root). Log: `/var/log/cloud-init-output.log`.
- **Jangan pernah masukkan secret di user data** — itu bisa dibaca lewat EC2 API dan metadata service. Ambil secret saat runtime dari SSM (Minggu 4).
- Batas: 16 KB.

### 4. Instance role bukan key

Satu instance profile adalah **lencana staff yang diklem ke mobil**, bukan key yang kamu salin: AWS berikan server credential sementara otomatis, dan mereka refresh sendiri.

Satu **instance profile** melampirkan peran IAM; AWS SDK dan CLI di instance ambil credential sementara otomatis.

| Managed policy / permission | Kenapa |
|---|---|
| `AmazonSSMManagedInstanceCore` | Session Manager, Run Command, patching |
| `ssm:GetParametersByPath` di `/revoshop/production/*` (+ `kms:Decrypt` untuk key-nya) | baca secret app saat deploy |
| `CloudWatchAgentServerPolicy` | kirim log/metrik dengan CloudWatch agent (opsional) |

### 5. Session Manager, bukan SSH

```bash
aws ssm start-session --target i-0123456789abcdef0                      # a shell, no port 22, no key pair
aws ssm start-session --target i-0123… \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["revoshop.xxxx.rds.amazonaws.com"],"portNumber":["5432"],"localPortNumber":["5494"]}'
# then: psql "postgresql://…@localhost:5494/revoshop"                   # reach private RDS from your laptop
```

Butuh Session Manager plugin untuk AWS CLI di laptop, instance role di atas, dan HTTPS keluar dari instance. Session tercatat di CloudTrail; kamu bisa simpan output session ke S3/CloudWatch.

### 6. IMDSv2

IMDSv1 jawab siapa pun yang tanya; IMDSv2 dulu butuh token, seperti resepsionis yang tanya nama sebelum kasih lencana. Satu pengaturan itu blok seluruh keluarga serangan.

Metadata service instance (`169.254.169.254`) bagikan role credential. **IMDSv2** butuh session token yang didapat dengan `PUT` request, yang blok kebanyakan serangan SSRF. Atur **metadata version: V2 only** (dan hop limit 1, atau 2 kalau container harus jangkaunya) di setiap instance.

### 7. Penyimpanan EBS

| Perilaku | Detail |
|---|---|
| **gp3** | pilihan default; atur ukuran, IOPS dan throughput terpisah |
| Enkripsi | aktifkan **EBS encryption by default** untuk account/region |
| Stop | instance berhenti; volume EBS (dan biayanya) tetap ada; public IP berubah (kecuali Elastic IP) |
| Terminate | root volume dihapus kalau "delete on termination" (default untuk root); volume ekstra mungkin tetap dan terus ditagih |
| **Snapshot** | backup incremental ke penyimpanan berbasis S3; otomasi dengan **Data Lifecycle Manager** atau AWS Backup |

### 8. Public IP, Elastic IP, proteksi

- Public IPv4 yang otomatis berubah saat stop/start; **Elastic IP** tetap sama (keduanya ditagih per jam untuk tiap IPv4).
- **Termination protection** dan **stop protection** cegah kecelakaan konsol.
- Kasih nama dan tag instance; aktifkan **detailed monitoring** hanya kalau kamu butuh metrik 1 menit.

### 9. Monitoring dan patching

- Metrik dasar CloudWatch: CPU, network, status check. Memory dan disk butuh **CloudWatch agent**.
- Alarm: `StatusCheckFailed` (dengan aksi **recover** otomatis), CPU credit balance, disk usage (agent).
- Patching: `unattended-upgrades` untuk security update, plus rebuild bulanan dari AMI fresh; **SSM Patch Manager** untuk fleet.

### Pilih setup-mu

Setiap pilihan di sini itu trade-off:

| Pilihan | ✅ | ❌ |
|---|---|---|
| EC2 + Docker Compose | kontrol penuh, paling murah selamanya untuk aplikasi kecil, stack sama dengan lokal | kamu patch, monitor dan scale OS; satu instance = satu titik gagal |
| Graviton (`t4g`) | harga lebih rendah untuk performa serupa | butuh image arm64 |
| Session Manager | tidak ada port terbuka, tidak ada key, diaudit | butuh agent + role + HTTPS keluar; setup kecil |
| SSH dengan key | universal | key bertebaran, port terbuka, audit lebih susah |
| Elastic IP | target DNS stabil | biaya IPv4; lebih baik kasih load balancer di depan untuk production sungguhan |

- ✅ Aplikasi kecil selamanya, software custom, belajar cara kerja server, beban kerja butuh akses OS khusus.
- ✅ Di belakang load balancer di Auto Scaling group untuk fleet stateless.
- 🚫 Jangan jalankan satu EC2 instance sebagai satu-satunya salinan data penting.
- 🚫 Jangan atur production server dengan tangan yang tidak bisa dibangun ulang dari kode.

## ⚠️ Kesalahan umum

- Deploy citra `arm64` yang dibangun di Mac ke instance x86 (`exec format error`).
- Security group biarkan SSH dari mana saja "hanya hari ini".
- Anggap public IP tetap sama setelah stop instance.
- Tulis secret ke user data atau AMI.

:::revoshop
1. **Pilih instance-nya.** Lab 2 pipeline-mu bangun citra `linux/amd64`, jadi **`t3.small`** (x86, 2 GB RAM) jalankan langsung; `t4g.small` (arm64, lebih murah) butuh `platforms: linux/arm64` atau build multi-arch. Mana yang kamu pilih, dan apa yang kamu ubah di `.github/workflows/ci-cd.yml` kalau pilih Graviton?
2. **Budget memory.** Di 2 GB kamu jalankan Caddy, gunicorn (`WEB_CONCURRENCY` dari `gunicorn.conf.py`) dan Redis — PostgreSQL pindah ke RDS. Mulai stack Lab 1 lokal tanpa service `db` dan cek `docker stats`. Berapa gunicorn worker yang muat, dan kamu butuh swap 1–2 GB dari latihan 04?
3. **User data untuk RevoShop.** Generate cloud-init-mu dengan `render_user_data(deploy_user="deploy", swap_gb=1, app_env={"APP_ENV": "production", "WEB_CONCURRENCY": "2"})`. Kenapa ia tolak `JWT_SECRET_KEY`, dan nilai itu datang dari mana?
4. **Instance role-nya.** Tulis policy least-privilege untuk instance RevoShop: Session Manager (managed policy), baca parameter `/revoshop/production/*`, decrypt dengan key SSM KMS, dan tarik dari GHCR (hint: itu bukan permission AWS — instance akan autentikasi ke GHCR bagaimana?).
5. **Tidak ada SSH.** Lab 2 `deploy.yml` kamu deploy lewat SSH. Sketch alternatif Session Manager: `aws ssm send-command --document-name AWS-RunShellScript` dari GitHub Actions dengan OIDC role. Mana lebih aman, dan permission apa yang GitHub role butuhkan?

## 🏆 Praktik terbaik

- [ ] AMI resmi terbaru; arsitektur cocok dengan image-mu.
- [ ] Ukuran yang tepat dengan pengukuran; awasi CPU credit di instance burstable.
- [ ] Bootstrap dengan user data/cloud-init (tanpa secret); bisa dibangun ulang dari awal.
- [ ] Instance role IAM dengan least privilege; tidak ada access key di instance.
- [ ] Session Manager; tidak ada inbound SSH; tidak ada key pair kecuali benar-benar perlu.
- [ ] IMDSv2 required.
- [ ] Volume gp3 ter-enkripsi; snapshot otomatis untuk apapun yang stateful; hapus volume orphan.
- [ ] Alarm status-check dengan auto-recover; security update aktif; termination protection.
- [ ] Tag: project, environment, owner.

## ✅ Cek cepat

:::quiz
API-mu di `t3.small` cepat pagi, lambat sore, dengan CPU "hanya" 30%. Apa yang kamu cek?

Balance CPU credit dan baseline: baseline `t3.small` adalah 20% per vCPU. Kalau credit habis (mode standard) instance di-throttle ke baseline; di mode unlimited kamu lihat biaya surplus credit. Pikirkan instance yang lebih besar atau bukan burstable, atau kurangi CPU use.
:::

:::quiz
Kenapa IMDSv2 bantu melawan SSRF?

Dapat credential butuh dulu dapatkan token dengan HTTP `PUT` dan custom header, yang SSRF vulnerabilities biasa (hanya buat `GET` request ke URL) tidak bisa; hop limit juga henti request yang diteruskan.
:::
